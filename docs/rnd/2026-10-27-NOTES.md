## New lever: P5, shared-prefix fan-out serialization

### The workload shape, and why it was studied

The mandate's multi-agent shape is "sub-agent fan-out re-sending shared
context." Checked how that fan-out is actually scheduled in the real
frameworks rather than assuming: LangGraph's `Send` API routes a list of
work items to N parallel graph nodes that the Pregel runtime executes
**together in the next super-step** — multiple independent sources
describe wall-clock time tracking the *slowest* branch, not the sum of
branches, because the branches are genuinely concurrent, not queued one
after another (checked via WebSearch against LangGraph docs/forum/case
studies, 2026-10-27; CrewAI's and AutoGen's parallel-task dispatch and the
Claude agent SDK's sub-agent spawn follow the same shape — a routing
function fires N calls together via `Promise.all`/`asyncio.gather`-shaped
concurrency, not a loop with deliberate spacing).

That matters because a provider prompt-cache entry does not exist for
anyone until the WRITING request's response has actually started. When N
sub-agents share one orchestrator-authored system prompt + tool catalogue
(the normal case — they are usually the same role template fanned out over
N work items) and are dispatched within the same instant, all N requests
race for a cache entry that is still being written by whichever one the
provider happens to answer first. Every one of them pays the Anthropic
write premium (1.25x/2x base); none of them reads at 0.1x. This is a
substrate defect in FLUX's OWN simulator's honesty, not a hypothetical:
`evals/run-workload-matrix.ts`'s existing `multiAgentTeam` fixture
staggers sub-agents **4 seconds apart within a round**, specifically so
each one already finds the previous one's entry waiting. The old
`cache-simulator.ts` made that stagger load-bearing by accident: a written
entry was instantly visible to any later request regardless of real
timing, so the simulator could never have told the difference between "4
seconds apart" and "same instant" even if the fixture had tried. This is
exactly `docs/rnd/lever-backlog.md`'s P5 finding, and its own measurement
plan said to fix the simulator "in the same change" as restating the band
— so that came first.

### What was built

1. **`packages/core/src/cache-simulator.ts`**: added `visibleAfterSeconds`
   to `SimulatedRequest` — how long after a request's own `atSeconds` its
   cache write becomes visible to OTHER requests (the write's own time to
   first response byte). Entries are now matched against candidates split
   into "already visible" vs "still racing"; a request that would have hit
   a prefix if only it had arrived a moment later now gets a distinct
   `missReason: "not-yet-visible"` instead of being silently folded into
   `"below-minimum"`/`"no-matching-prefix"`, so a race loss is
   distinguishable from a genuinely absent prefix in any future report.
   **Default is 0 (instantly visible)** — unchanged from before the field
   existed — so every existing eval, including `run-workload-matrix.ts`'s
   4-second-staggered multi-agent fixture, is bit-for-bit unaffected; the
   field only engages when a caller explicitly sets it to model genuine
   concurrency, which until tonight nothing in the repo did. 4 new tests in
   `cache-simulator.test.ts` (default-unchanged, two simultaneous writers
   both miss, a later arrival reading once the writer's response has
   actually started, and race-loss vs absent-prefix distinguished).

2. **`packages/sdk-js/src/fanout-latch.ts`** (new): `createFanOutLatch()`,
   the lossless lever itself. The first caller for a shared-prefix key
   becomes the "leader" and sends immediately; every caller arriving while
   that leader is in flight becomes a "follower" and awaits release, which
   fires the instant the leader's response starts (or errors) — a follower
   NEVER waits past a bounded hold timeout (default 10s) regardless of
   what the leader does, so the latch can only ever convert a write into a
   read, never add an unbounded stall or drop a request. `fanOutLatchKey()`
   derives the shared-prefix identity from provider + model + system +
   tools — deliberately coarser than FLUX's own stamped breakpoint bytes
   (the live byte-match of FLUX's hashing against the provider's actual
   cache keying is still an open item per lever-backlog.md's P5 condition
   7 and open-questions #3), which is safe to ship ahead of that
   verification because the only cost of a wrong key match is a few
   seconds of needless holding, never a wrong answer or a dropped request.
   10 unit tests: leader/follower assignment, release on both success and
   error paths, the bounded timeout under fake timers, independent keys,
   idempotent double-release, and the no-op case for a lone key.

3. **`packages/sdk-js/src/proxy.ts`**: wired the latch in behind a new
   `serializeFanOut` option (default `false`). Only engages for
   Anthropic-shaped requests the proxy is actually configured to stamp
   (`reduction.cacheTtl !== undefined`) — an unstamped request has no
   cache entry for a sibling to race against in the first place. The
   leader's own `fetch()` call resolving is literally "the response has
   started" (fetch/undici resolves once headers arrive, before the body
   streams), so `release("started")` fires at exactly the right moment
   with no extra plumbing; `release("errored")` fires on the existing
   upstream-unreachable catch path, which already handles every other
   failure mode identically. 2 new integration tests in `proxy.test.ts`:
   one proves a follower's request literally does not reach the real
   upstream until the leader's response headers have already been sent
   (using a stub that deliberately delays the leader to make the ordering
   observable), the other proves the flag is a no-op when no `cacheTtl`
   is configured.

4. **`evals/run-fanout-serialization.ts`** (new): the fixture and
   measurement. A realistic fan-out — one shared ~1,741-token
   orchestrator system+tools prefix, 4 sub-agents dispatched at the
   identical instant per round, 6 rounds spaced 400s apart (deliberately
   PAST the 300s TTL, so every round is its own fresh cold-start race
   rather than letting round 0 alone absorb the whole cost and understate
   the recurring one) — run through the corrected simulator two ways: (a)
   naive concurrent dispatch, today's actual behavior, and (b) the latch's
   effect modelled as holding followers until `atSeconds + writeTtfb`,
   exactly what `fanout-latch.ts` does in production, with not one byte of
   either prompt touched.

### Measured result

```
shared prefix: 1741 tokens (clears the 1024-token minimum)
estimated write TTFB 0.84s (ESTIMATE — see below)
6 rounds x 4 agents, identical instant per round, 400s apart (fresh cold start each round)

naive concurrent (today, no latch)   $0.1493  hits  0%  miss reasons: {first-request:1, not-yet-visible:18, expired:5}
FLUX latch (serializeFanOut: true)   $0.0736  hits 74%  miss reasons: {first-request:1, expired:5}

latch-alone saving vs naive concurrent: 50.7% ($0.0757)
```

18 of 24 requests in the naive arm are `not-yet-visible` — real race
losses, not absent prefixes — and every one of them disappears with the
latch (0/24). The per-racer arithmetic checks out against the documented
rates independently of the simulator: a racing 1,741-token write costs
1.25x base; the same tokens read cost 0.1x; (1.25−0.1)/1.25 ≈ 92% per
racer, which is exactly the lever-backlog's own formula — the blended
50.7% is lower than that because it also carries the leader's own
unchanged cost, the output tokens, and the unique per-agent tail that was
never cacheable either way.

### Honesty labels (read before anyone quotes this)

- The cache mechanics (minimum prefix, TTL, multipliers, and now the
  visibility delay) are the same documented-rules simulator every other
  published number in this repo uses: **simulator-measured**.
- The write time-to-first-byte (0.84s for this prefix size) is an
  **ESTIMATE** — no capture in this repo carries request timestamps
  (lever-backlog.md open-question #3, still open). Chosen conservatively
  small, which if anything understates the race's real cost.
- The fixture is a **designed 100%-collision** fan-out, built to isolate
  the race in the cleanest case. The real fleet-wide collision frequency —
  what share of actual multi-agent traffic fans out this tightly — is
  **UNMEASURED**, exactly as lever-backlog.md's P5 already says. 50.7% is
  not a claim about aggregate customer savings; it is a claim about what
  this specific, real, documented race costs when it happens, and that the
  latch removes it losslessly when it does.
- `serializeFanOut` defaults to **off**. Per the backlog's P5 adversarial
  conditions, still open before this could ever default on or bill
  anything: live byte-match of FLUX's prefix key against the provider's
  real cache key; production latency/timeout/429 telemetry on the held-
  request path; per-prefix auto-disable on repeated timeout misses. None
  of that exists yet. Tonight's work is the mechanism plus its measured
  ceiling, not a production rollout.
- No new ledger lever was added, and none was needed: if this ever ships
  live, its effect shows up automatically as improved
  `cache_read_input_tokens` in the provider's own usage object, already
  priced by the existing `normalizeProviderUsage` / `priceLedgerUsage`
  pipeline — the lever changes send TIMING only, so the existing honest
  pricing path already covers it without any new billing code.
