## Hardening: profiling and cutting `reduceRequest`'s per-request CPU cost

### The problem

`evals/run-proxy-overhead.ts` on this session's container (linux/x64, a
cloud sandbox — not the darwin/arm64 machine the published ~22ms figure
was measured on, so the absolute numbers below are not compared against
that published figure; see the caveat already in `evidence.md`) measured
the proxy adding a mean of **47.33ms** per request over a direct call to
an instant loopback stub, across three interleaved runs. That is a large
number for pure in-process work with no real network or provider latency
in it, so it was worth finding out where it actually goes rather than
accepting "the container is slow" as the explanation.

Isolating the proxy's own request-path work from HTTP/Node mechanics
(`/tmp` micro-benchmark, not committed — calls `reduceRequest`,
`createHash`, and `ledger.emit` directly against the same fixture bodies
`run-proxy-overhead.ts` uses, bypassing the HTTP layer):

| component (1600 ops) | per-op |
|---|---|
| `JSON.parse(body)` | 0.027ms |
| **`reduceRequest()`** | **4.43ms** |
| `JSON.stringify(reduced)` | 0.046ms |
| `sha256(body)` dup-hash | 0.036ms |
| `ledger.emit()` | 0.040ms |

`reduceRequest` was ~100x every other step combined. A second
instrumented run (wrapping `countTokens` to log call count, total
characters scanned, and time spent) on the full lossless stack +
`historyCompaction` + `cacheTtl: "5m"` config `run-proxy-overhead.ts`
itself uses:

- **103.3 `countTokens` calls per request**, scanning **125,536
  characters per request** — roughly **6x** the request's own ~20KB JSON
  size.
- **88.1% of `reduceRequest`'s wall time spent inside `countTokens`**
  (`approximateTokenCount`, `packages/core/src/token-reduction.ts`).

The counter itself is doing legitimate, intentionally-approximate work
(Unicode-aware word/punctuation scanning, ~0.5ms on a 17KB string — see
its own docstring: "+/-15% against a real tokenizer, good enough to rank
candidate reductions, not good enough to bill on"). The bug is not in the
counter; it is that `reduceRequest` and the functions it calls
(`minifyToolSchemas`'s own before/after/pretty-after totals,
`stampAnthropicCacheTtl`'s three prefix-size checks, the top-level
before/after summary totals) each independently re-stringify and re-count
overlapping slices of the same tools array and message history, several
times per request, with no memoization between them. `countTokens` is
documented and relied upon elsewhere in this same file as a pure function
of its string argument (e.g. `capToolResultBody`'s idempotence depends on
it), so nothing stops caching it.

### The fix

`packages/sdk-js/src/reduce-request.ts`, `reduceRequest()`: wrapped the
caller-supplied (or default `approximateTokenCount`) counter in a
`Map`-keyed memo, scoped to the single `reduceRequest()` call and
discarded when it returns — no cross-request state, no memory growth,
no staleness risk, because nothing here ever mutates a string in place
and the cache never outlives one call. Every downstream function already
receives `countTokens` as a parameter from this one local variable, so
this is a single-point change with no call-site edits anywhere else.

This is provably behavior-preserving: a pure function memoized by its
exact input is observationally identical to the unmemoized version, for
every caller. It is not a new transform on model-visible content, so no
quality gate or replay-gate pass applies — the same category as any other
pure refactor.

### Measured effect

Confirmed zero drift first: `pnpm build` clean, **435/435 tests pass**
(433 existing + 2 new, below), and `run-cache-decomposition.ts` reproduces
**37.9% / 57.3% / 31.3%** unchanged to the decimal — exactly as expected
for a pure cache with no behavior change.

Direct profiling instrumentation, same fixture, same config, before vs.
after (400 `reduceRequest()` calls):

| | before | after | change |
|---|---|---|---|
| wall time | 5.076ms/req | 3.476ms/req | **−31.5%** |
| `countTokens` calls | 103.3/req | 78.9/req | −23.6% |
| characters scanned | 125,536/req | 79,167/req | −36.9% |
| time inside `countTokens` | 88.1% of wall | 81.0% of wall | — |

End-to-end, `evals/run-proxy-overhead.ts` (800 req/arm, concurrency 8,
same container, three runs for stability):

| | before | after (run 1) | after (run 2) | after (run 3) |
|---|---|---|---|---|
| mean added latency | 47.33ms | 33.73ms | 33.15ms | 34.71ms |
| p50 added | 45.96ms | 33.18ms | 32.77ms | 33.91ms |

**~27–30% reduction in the proxy's own added latency**, reproducible
across repeated runs. This is a same-machine, same-config before/after
comparison; it is not a revision of the published ~22ms/darwin/arm64
figure, which this session never re-measured and so cannot honestly
confirm or revise — `docs/site/evidence.md` now carries both figures
side by side with that distinction stated explicitly. The underlying win
(CPU time removed) is architecture-level, not container-specific, so it
should reproduce as a relative improvement on any machine, including the
one the published figure cites — worth a follow-up re-run there if this
session or a future one ever has access to it.

### What was NOT touched

- `approximateTokenCount` itself is unchanged — its cost-per-character is
  a real tradeoff (Unicode-correct word/punctuation boundaries vs. a raw
  `length/4` estimate, ~5000x cheaper but far less accurate per the
  earlier micro-benchmark) and changing it would be a precision/risk
  decision, not a pure performance one. Out of scope tonight.
- `minifyToolSchemas`'s three big counts (pretty-before, compact-after,
  pretty-after) were NOT collapsed into fewer measurements: the
  pretty-vs-compact distinction is the "formatting" lossless-saving claim
  itself (a real published lever, not a performance artifact), so
  removing any of those three measurements would change what gets
  reported, not just how fast it runs. The memo still catches the cases
  where its output happens to be re-measured identically elsewhere later
  in the same request (confirmed in the instrumented count-per-request
  drop above).
- No change to `savings-ledger.ts`, `proxy.ts`'s HTTP/streaming mechanics,
  or the `sha256` dup-hash — each measured far cheaper than
  `reduceRequest` in the component breakdown above and were left alone
  this cycle.
