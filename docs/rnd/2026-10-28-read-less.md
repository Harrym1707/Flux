# R&D 2026-10-28: "read less", type-aware compression of fresh tool output

Branch `rnd/2026-10-28-read-less`. All numbers below are **SIMULATOR**
numbers (see `docs/NUMBERS.md`). They are not live and not billable as
they stand. The lossy share also needs a replay-gate verdict before it can
bill.

## Why

Caveman (YC F26) reports its best measured result, 33% fewer input tokens
across 54 Claude Code runs, from a layer that compresses tool output by type
before the model reads it. Until now FLUX compressed only STALE tool results
(`historyCompaction`, `semantic-compaction.ts`) plus a type-blind cap on
oversized fresh results. A 200-line test run with one failure went in almost
untouched on its first send, which is the full-rate one.

## What was built

`packages/sdk-js/src/tool-output-compression.ts`, wired into `reduceRequest`
(`packages/sdk-js/src/reduce-request.ts`) as `toolOutputCompression`. It is
**off by default**. It runs before `freshToolResultCap` and
`historyCompaction`, so those levers see bodies that are already compressed
and deterministic.

| Toggle | Transform | Label |
|---|---|---|
| `json` | whitespace-only minification by a string-aware scanner; every literal (big ints, `1.0`, escapes, duplicate keys) kept byte-for-byte | lossless |
| `logs: "lossless"` | strip ANSI SGR colour codes; collapse runs (>=3) of exactly identical lines into `line (xN)` (expanding the marker gives back the input, which a test checks) | lossless |
| `logs: true` | the lossless tier, plus: all escape sequences, carriage-return overwrites resolved to the final frame, progress-bar lines dropped, runs of near-identical lines (equal once timestamps, hex and numbers are masked) collapsed to the first line plus `(xN, timestamps/numbers vary)` | lossy |
| `testOutput` | runs of passing-test lines collapsed to `[flux: N line(s) of passing tests collapsed: K passed]`. Formats: jest, vitest, mocha, pytest -v, pytest default, go test -v, cargo test. Every failure, stack trace, code frame and summary line is kept verbatim | lossy |
| `installOutput` | npm http/timing, pnpm Progress and `+++` lines, yarn steps, pip Collecting/Downloading, cargo Downloaded/Compiling runs (>=3) become a count marker plus the run's last line | lossy |
| `jsonDropEmpty` | drop object members that are null, `""`, `[]` or `{}` (recursively; array positions kept), plus a trailing marker | lossy |
| `csv` | header, first and last K rows (default 10), and a row-count marker. Applies only when every line has the header's field count | lossy |
| `html` | full HTML documents only: script/style/svg/template/noscript/head/comments removed, tags reduced to text, headings kept as `#`, list items as `- `, links kept as `text (href)`, `<pre>` whitespace kept | lossy |

`toolOutputCompression: true` turns on the **lossless tier only**
(`{ json: true, logs: "lossless" }`), the same convention `toolSchemas: true`
uses. Savings go to two lever ids. `tool-output-compression` is
`lossless: true`. `tool-output-compression-lossy` is `lossless: false`, and
the savings ledger bills it only when `gateVerdicts["tool-output-compression-lossy"]`
is an approved replay-gate verdict (`replay-gate.ts`, enforced in
`savings-ledger.ts`). Lossless stages always run first, so the split is exact:
lossless saving is raw minus lossless-only, and lossy saving is lossless-only
minus final.

### Hard requirement 1: byte stability (the P7 trap)

Each body is compressed by a **pure function of (its own text, its own tool
call, the options)**. Nothing depends on turn index, message count, other
bodies or a moving window. So a result is compressed on the turn it first
appears, and every later turn re-sends the same raw result and gets
byte-identical compressed bytes. There is no cut schedule that could slide.
The tool name and command come from the assistant `tool_use` /
`tool_calls` / `function_call` that issued the call. That message is history
by the time the result exists, so the lookup is as stable as the result.

The proof is in these tests:
- `tool-output-compression.test.ts`, "is byte-stable across turns". Every
  reduced request's message history is an exact prefix of the next one's,
  and its wire string literally extends the previous one. The same check
  runs stacked with `freshToolResultCap`.
- "a tool result is compressed on the turn it first appears, identically
  every later turn".
- `evals/run-tool-output-compression.ts` asserts the prefix property for
  every arm and exits non-zero if it fails. All arms report `byte-stable: true`.
- Every fixture is checked for determinism and idempotence under the full
  config.

### Hard requirement 2: what is never touched

- Only tool-result carriers are visited: Anthropic `tool_result` blocks,
  Chat `role: "tool"` messages and Responses `function_call_output`. Model
  output, user text and system/developer text never reach the compressor
  (there is a test for this).
- Results from file read/edit tools (`Read`, `read_file`,
  `str_replace_based_edit_tool`, `Edit`, `Write`, `view`, `cat`, MCP
  `*__read_file`, …, plus a caller list in `verbatimTools`) always pass
  through verbatim.
- Shell commands that dump a file pass verbatim. That means any statement
  starting with `cat`/`head`/`tail`/`sed`/`awk`/`bat`/`nl`/`less`/…, so
  `cat package.json | jq .` is left alone and `pytest | tail -50` is not.
  An agent that edits what it just read must see the bytes on disk.
- Numbered file listings (cat -n), diffs, anything with a code fence, and
  binary-ish bodies (NUL bytes, or more than 1% control characters) pass
  verbatim.
- Detection is conservative. JSON must `JSON.parse` end to end. HTML must be
  a document (`<!doctype html` / `<html`); fragments are left alone. CSV
  needs consistent field counts on every line and at least 2K+5 rows. Test
  collapsing needs a real runner summary signature plus at least 3 pass
  lines. Install collapsing needs at least 5 package-manager lines. Log
  collapsing needs at least 60% timestamped/levelled lines. A unit test
  checks that this module's sibling source file, printed by a non-read tool,
  comes through untouched.
- Lines that mention error/fail/warn/panic/assert/deprecated/vulnerab… are
  never collapsed or dropped. pnpm's ` WARN ` badge line is kept
  byte-for-byte.
- An "accounting" test covers 8 real captures. Every output line that is not
  a marker appears in the input in order, and kept plus marker-counted lines
  equals the input line count exactly.

## The eval

`node --import tsx evals/run-tool-output-compression.ts` (also
`pnpm readless:eval`). It is a 15-step Claude Code-shaped session in
Anthropic Messages format, one request per assistant step, with the full
raw history re-sent every turn and 20 s between requests. The steps are:
pnpm add, jest (failing), Read of the test file, npm registry JSON, the
nodejs.org page, pip install, pytest -v, PyPI JSON, go test -v,
cargo build, cargo test, the service log, a CSV query, Edit, and jest
(passing).

Every arm carries the lossless stack (`toolSchemas`, `duplicateContext`,
`repairCachePrefix`) **and FLUX's 5m cache stamp**, and the stamp is placed on
15/15 requests in every arm. So the savings are **net of caching**: a
history token this lever removes is valued at what it would have cost as a
cache read, not at full rate. Arms are priced two ways at catalogued
claude-sonnet-5-5 rates ($2/M input, $10/M output, catalogue date
2026-10-27):
1. `packages/core/src/cache-simulator.ts`, `ANTHROPIC_CACHE_5M`, which the
   task requires.
2. A breakpoint-exact cross-check (the `run-workload-matrix.ts` rule): a
   read needs a previously written breakpoint span to prefix the request,
   and the newly stamped suffix is billed as a 1.25x write. The longest-prefix
   simulator bills that suffix at 1x and so understates write premiums.

**Token counter: `approximateTokenCount` (FLUX's default).**
`packages/core/src/openai-tokenizer.ts` does not exist on main. An OpenAI
tokenizer would also be the wrong counter for a Claude request.

### Caveats (read before quoting anything)

1. **One synthetic session, n=1.** The bodies are real captures, but the
   session's choice and order of tools is ours. Caveman's 33% comes from 54
   real runs; our numbers are a different kind of measurement and must not
   be set beside theirs as a head-to-head.
2. **The HTML arm is dominated by one extreme body.** A raw `curl` of a
   Next.js page is 140k approximate tokens, mostly inline script. Claude
   Code's own WebFetch already returns markdown, so the 90% figure applies
   only to raw-curl agents. That is why the no-HTML session is reported.
3. **The CSV body is large (775 rows, 16k tokens) and the lossy saving tracks
   it.** An agent that adds `| head` itself would leave little to save. The
   per-type table is there so nobody has to trust the blended number.
4. **The lossless tier is understated for JSON.** `approximateTokenCount`
   counts runs of whitespace as zero tokens, except newlines. Real BPE
   tokenizers do emit tokens for indentation, so the 5% JSON saving is a
   floor. A count_tokens calibration (lever-backlog P1.5) would settle it.
   The `test` lossless figure is a true 0%: plain test output has no colour
   codes or exact repeats to remove.
5. **Lossy quality is not measured here.** No model is called. Passing-test
   names, install chatter, varying timestamps (the log collapse hides which
   `?page=N` requests ran), CSV middle rows, null fields and HTML markup are
   all gone. Every failure and summary line is kept, but whether an agent
   still finishes its task is a replay-gate question
   (`replayGate` with an agent grader on the customer's own traffic), and
   `tool-output-compression-lossy` bills nothing until that verdict approves it.
6. **The guards cost savings on purpose.** `tail -n 200 app.log` and
   `cat test-output.txt` pass verbatim, because a statement that starts with
   a file-dump program is treated as a file read. The eval's log step uses
   `docker compose logs`. A looser guard would save more and risk handing a
   compressed file to an Edit call.
7. **Simulator limits.** The longest-prefix simulator does not charge a
   write premium on suffix extensions (see the cache-write column). The
   breakpoint-exact pricer does, and it agrees within 1 point on every arm.
   Neither is a live bill.
8. **Not yet in the published numbers.** `docs/NUMBERS.md` is unchanged.
   Nothing here is LIVE.
