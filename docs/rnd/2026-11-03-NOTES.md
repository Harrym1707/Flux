## Hardening: closed the semantic-compaction cross-turn-stability blocker

`docs/rnd/semantic-compaction-design.md` (2026-10-27 review) flagged a **hard blocker**
on the local-model semantic-compaction prototype (`packages/sdk-js/src/semantic-compaction.ts`,
still OFF by default, double-gated, not shippable): a stale tool-result body is RESENT
every turn, and the compactor is a non-deterministic model, so re-invoking it fresh on
every call would re-paraphrase an already-compacted body differently each time —
busting a provider's exact-prefix cache every single turn. The note was explicit that
this "MUST NOT be enabled alongside caching until the compacted result is pinned."

### What was built

- `packages/sdk-js/src/compaction-pin-store.ts` — new `CompactionPinStore` class.
  Hash-keyed (sha256 of `[kind, maxTokens, text]`, same pattern as
  `CachePrefixVolatilityGuard`'s `digest`), bounded LRU (default 5,000 entries,
  constructor-validated). `get`/`set` pin the OUTCOME of compacting one exact body —
  including the "compactor returned nothing shorter, use the original" outcome, not just
  successful compactions — so a body is never re-sent to the (possibly slow, possibly
  metered-by-latency) local model more than once, either.
- Wired into `semantic-compaction.ts` as `SemanticCompactionConfig.pins`: before calling
  the customer's compactor on a target body, `compactStaleContext` checks the pin store
  first; a hit short-circuits the compactor call entirely and reuses the prior decision
  byte-for-byte. Backward compatible — omitting `pins` keeps the exact old per-call
  behaviour (correct in isolation, just not cross-turn stable), so no existing caller or
  test needed to change.
- Exported via `packages/sdk-js/src/index.ts` (`CompactionPinStore`, `CompactionPinOutcome`).
- Usage pattern matches `CachePrefixVolatilityGuard`'s documented contract exactly: the
  caller creates ONE instance and reuses it across every call for the life of the
  proxy/process. This lever is not wired into `proxy.ts` yet (it remains a standalone
  prototype — see the design doc's still-open items 1-4), so no proxy wiring was added;
  this was scoped to the pinning mechanism itself and its tests, per the hardening
  mandate ("harden existing levers' edge cases with tests").

### Tests added (12, all passing)

- `packages/sdk-js/src/compaction-pin-store.test.ts` (6): miss-then-hit, pins the
  "nothing shorter" outcome, keyed on exact text / maxTokens / kind (each a separate
  entry), constructor validation, and LRU eviction behaviour (a `get()` counts as use).
- `packages/sdk-js/src/semantic-compaction.test.ts`, new `describe` block (6): an
  `unstableCompactor` stub that returns a different numbered summary on every call
  (standing in for a real model's turn-to-turn variance) proves (a) WITHOUT `pins`, the
  same stale body compacts to different bytes on repeated calls — the failure the
  blocker described, now reproduced directly; (b) WITH a shared `pins` store, three
  repeated calls on the same conversation produce byte-identical compacted bodies, and
  the compactor runs exactly once per unique body, never once per call; (c) the "nothing
  shorter" outcome is pinned too; (d) a genuinely different body (one byte changed) is
  correctly treated as a new, unpinned entry — pinning never papers over a real content
  change; (e) `reduceRequestAsync` threads `pins` through end-to-end.

### Measured: the blocker was real, and pinning fixes it

New eval: `evals/run-semantic-compaction-pin-stability.ts`. A 24-turn simulated
always-on agent conversation (30s apart, Anthropic 5m cache policy, ~1,300-tok static
system preamble so the cacheable minimum is cleared from turn 1), three arms on
identical underlying traffic:

```
A. no compaction                cost $0.1563  hit rate 92.6%
B. compaction, UNPINNED          cost $0.1672  hit rate 46.8%  compactor calls 253
C. compaction, PINNED            cost $0.1479  hit rate 55.9%  compactor calls 22

B vs A (unpinned compaction vs doing nothing): -7.0%  <- NEGATIVE: unpinned compaction is MORE expensive than doing nothing
C vs A (pinned compaction vs doing nothing):   5.4%
C vs B (pinning fixes the unpinned regression): 11.6%
compactor invocations avoided by pinning: 231 of 253 (local compute, not billed tokens, but real latency/cost on the customer's own machine)
```

Honest reading, per the mandate ("a lever that loses money counts against FLUX"):

- **Unpinned semantic compaction, stacked with caching, is confirmed to lose money**
  (−7.0% vs doing nothing at all) — this was a real, measurable loss, not a theoretical
  worry. Good that it was caught and gated off by default before anyone could enable it.
- **Pinned, the lever flips to a modest net positive** (+5.4% vs doing nothing, +11.6%
  vs the unpinned arm) on this fixture. 5.4% is a small number next to the 37.9%/57.7%
  headline levers and should NOT be quoted alongside them — it is reported honestly as
  what this specific fix is worth on this specific fixture, nothing more.
- A second, independent benefit not captured in the dollar figure: pinning cut local
  compactor invocations by 91% (231 of 253) on the same traffic. The compactor runs on
  the customer's own machine and costs zero tokens, but it is not zero cost — a
  quantised local model still burns real CPU/GPU time and adds real latency per call.
  Avoiding 9 out of 10 redundant invocations is a genuine operational win on top of the
  token-side number, worth mentioning to design partners even before a token figure can
  be billed.
- The compactor used is a STUB (`unstableCompactor`, a numbered marker string) standing
  in for a real model's non-determinism, same honesty label every other evals/ cache
  simulation carries: **simulator-measured, not provider-measured.**

This fix does NOT make semantic compaction shippable. The design doc's remaining open
items (1: a real local-model adapter, 2: calibration at larger n — separately tracked, 3:
a replay-gate eval with a paraphrase-aware grader, 4: no published savings number until
that gate runs on real customer traffic) are all still open and are correctly still
flagged as such in `docs/rnd/semantic-compaction-design.md`. Nothing here is billed or
claimed in README/evidence.md; this is purely a prototype hardening fix plus its own
measurement, consistent with "quality gates only get stricter" and "estimates are always
labelled."
