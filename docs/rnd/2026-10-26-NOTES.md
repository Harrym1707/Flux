## New-lever research: replay-gate-proving `crossTurnMemoryDedup`

### The gap this closes

`crossTurnMemoryDedup` (continuous-memory agents, founder mandate shape
list item 3) has been sitting in an unusual state for three nights: a real,
measured 58.0% token saving, explicitly classified LOSSY by its own author
on 2026-10-23, wired behind an opt-in config flag, gated in *prose*
("needs a replay-gate pass… before it may ever be billed") — but never
actually run through `packages/sdk-js/src/replay-gate.ts`, the production
approval machinery that `evals/run-replay-gate-freshcap.ts` already uses
for the fresh-tool-result cap. A lever that says "ask the gate" but has
never been asked is a gap in the evidence chain, not a finished candidate.

The honest obstacle, named plainly in 2026-10-23's own NOTES: there is no
live customer traffic or API budget in this environment, so a real
LLM-judge pass is not available here. What follows is the credible proxy
that same note asked for — built and labelled so nobody downstream mistakes
it for a production quality certification.

### What was built

**`evals/memory-recall-fixture.ts`** — a new continuous-memory-agent
fixture, purpose-built for a quality signal (the existing
`run-memory-agent-dedup.ts` fixture only ever measured tokens, never
correctness, because its turns never actually test recall of anything).
Eight independent facts (unit preference, deploy window, staging DB
schedule, an incident root cause, etc.), each its own short clause with no
shared content words, assembled into one `MEMORY_BLOCK`. Every 5th of 40
turns is a "recall probe" asking about one fact, rotating through all
eight exactly once per 40-turn conversation; the other turns are generic
filler, unaffected by the lever either way.

The simulated provider's `answerProbe()` decides correctness by reading the
**actual wired content of the current request** — exactly the house
convention `evals/agent-fixture.ts`'s `answer()` already uses (check the
request, never which arm is running): if the needed fact's clause is still
adjacent in the current turn's text, recall is certain; if only a dedup
marker is present, recall follows a distance-based probability curve, with
the draw made by a seeded deterministic PRNG (`mulberry32`) keyed on
`(arm, conversation, turn, fact)` so results are reproducible run to run.
This makes the SAME provider function correct for both the unreduced
baseline (fact always adjacent, distance 0, probability 1 by construction)
and the `crossTurnMemoryDedup`-reduced candidate (fact adjacent only in
turn 1; every later probe sees the real distance).

**The quality curve is explicitly synthetic — stated three times in the
file and script so it can't be missed**: a decay shape chosen to be
*qualitatively* consistent with the published "lost in the middle" finding
(Liu et al. 2023 — recall of information far from the most recent context
degrades) and tuned only for a visibly graded curve across this fixture's
turn range, not fit to any dataset or calibrated to any real model. Two
variants are provided: an ADVERSARIAL curve (up to a 65pp recall drop by
the last probe) and a MILD one (up to 6pp). Picking the mild curve's exact
rate (0.015, floor 0.9) took a short empirical search recorded in its own
comment — tried 0.03/0.85 (rejected, too close to the floor) and 0.008/0.95
(trivially approved at exactly zero delta, uninteresting) before settling
on a midpoint that clears the budget with visible room, not hunted to the
edge of passing.

**`evals/run-replay-gate-memory-dedup.ts`** — runs
`packages/sdk-js/src/replay-gate.ts`'s actual `replayGate()` (not a
reimplementation) over 8 independent 40-turn conversations (320 requests),
grouped by conversation for the bootstrap (every turn of one conversation
shares a fate — the same convention `run-replay-gate-freshcap.ts` uses,
grouping by task), graded with the existing continuous
`textSimilarityGrader` from `graders.ts` (word-overlap F1, so a wrong
recollection scores near 0 rather than being forced into a binary
pass/fail). Two passes:

1. **Adversarial curve.** Lossless-only candidate: exactly 0pp delta (it
   never touches the memory block) but *also* rejected, correctly, because
   it saves nothing on this shape — "quality held but neither tokens nor
   cost fell" (expected: the shape's prefix is below the 1,024-token
   cacheable minimum, same finding as last night's hardening fix).
   `crossTurnMemoryDedup`: 64.7% input tokens saved, but mean quality delta
   −9.78pp, lower-95 bound −11.97pp — **REJECTED**, breaching the default
   2% budget by a wide margin.
2. **Mild curve.** Same lever, same 64.7% token saving, mean delta −0.89pp,
   lower-95 bound −1.51pp — **APPROVED**, within the default 2% budget.

**`evals/run-replay-gate-memory-dedup.test.ts`** — 8 new tests pinning: the
probe schedule and fact rotation; `recallProbability(0) === 1` exactly (the
baseline must never be self-penalised by this model); the curve is
monotonic and respects its floor; `answerProbe` reads distance from actual
request content, not a label, verified against both an unreduced and a
hand-stripped request; `crossTurnMemoryDedup` as *actually wired* through
`reduceRequest` produces the content this fixture's distance model expects
(block kept at turn 1, marker from turn 2 on, probe distance matches turn
index); the lossless-only candidate holds exactly zero delta; the
adversarial pass rejects with a lower bound breaching −2%; the mild pass
approves with positive token savings. 394 → 402 tests.

### Honest framing of the result — read this before citing either number

**Neither pass is a verdict on whether `crossTurnMemoryDedup` is safe to
bill on real traffic.** Both decay curves are synthetic stress tests,
chosen for shape, not measured from any model and not fit to data. What
this work actually demonstrates, and the only thing it claims:

1. **The gate has teeth.** Run against a degradation shaped like the
   published long-context risk this lever's own LOSSY classification
   names, at a size a real "lost in the middle" effect could plausibly
   produce, the gate correctly refuses to approve it — it does not wave
   the lever through on "the bytes are identical" alone, which is exactly
   the failure mode 2026-10-23 worried about and nobody had actually
   tested until tonight.
2. **The gate is not a blanket rejector of lossy levers either.** Run
   against a small, equally plausible degradation, the same gate, same
   code path, same lever, approves it. The verdict tracks the *size* of
   the assumed cost, which is the property that has to hold before any
   customer should trust this machinery with their own pass.

`crossTurnMemoryDedup` remains exactly where 2026-10-23 left it: an
opt-in, off-by-default, LOSSY candidate at a measured 58.0% token saving,
now with a demonstrated (not merely asserted) gate-compatible evidence
path, but still requiring a REAL replay-gate run — a customer's own
traffic, a real grader, ideally an actual LLM judge — before any part of
its saving may be billed. Nothing in `README.md` or `docs/site/evidence.md`
changed or needed to: this was never a published number and still isn't.

### Quality gate / replay-gate status

This *is* the quality-gate work for this lever — the first time it has
run through `replayGate()` at all. The verdict is correctly mixed (reject
under the adversarial assumption, approve under the mild one), which is
the expected and desired outcome of a working gate facing an honestly
uncertain real-world risk, not a pass/fail result to report as one number.
