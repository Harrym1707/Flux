## Step 4 — hardening: proxy overhead

**Finding:** `node --import tsx evals/run-proxy-overhead.ts` on this
container (linux/x64, cloud session) measured FLUX's added latency at
**p50 ~62 ms / p95 ~79 ms / p99 ~90 ms** at the eval's default concurrency 8 —
nowhere near the documented ~22 ms p50 (measured darwin/arm64, 2026-10-20).
Before assuming a regression: the doc already caveats "absolute values vary by
machine — rerun on yours," and a sweep across concurrency (1/2/4/8) showed the
**FLUX-added** overhead (proxied − direct) scaling almost linearly with
concurrency (7.4 ms → 14.7 ms → 28.0 ms → 62.4 ms) while the "direct" control
arm barely moved. That is the signature of synchronous CPU work serializing on
Node's single event-loop thread under concurrent load, not a different
baseline machine speed — worth profiling regardless of the absolute-number
caveat.

**Root cause (CPU-profiled with `node --cpu-prof`, concurrency 8, 300 req):**
`approximateTokenCount` (`packages/core/src/token-reduction.ts`) — the counter
every lossless reducer calls to decide what to cut, and to report
tokens-before/after per lever — was **38.2% of all CPU samples** by itself,
plus three more regexes it invoked (14.3% combined) = **>52% of FLUX's own
per-request CPU time** going into one function.

The cause inside that function: for every chunk the tokenizing regex matched
(one of three alternatives — word run / symbol run / whitespace run), the code
ran **two more regex `.test()` calls** against the already-matched chunk just
to figure out *which* alternative had matched, even though the matching regex
already knows. Three regex engine invocations per chunk instead of one.

**Fix:** give the three alternatives capturing groups
(`([\p{L}\p{N}']+)|([^\p{L}\p{N}'\s]+)|(\s+)`) and read which group is defined
off the single `matchAll` match — zero extra passes over the text. Newline
counting inside whitespace runs was also switched from a second regex
(`chunk.match(/\n/g)`) to a `charCodeAt` loop, since whitespace runs are short
and this avoids spinning up another regex object per whitespace chunk.

This is **behavior-preserving, not an approximation change**: the three
alternatives are mutually exclusive and exhaustive over the original pattern,
so which capture group is defined is the identical classification the two
`.test()` calls were recomputing. Verified three ways:
1. 14 new pinned exact-value test cases (`token-reduction.test.ts`) covering
   empty string, pure whitespace, newline runs mixed with whitespace, words,
   digits, apostrophes-inside-words, punctuation runs, single chars (the
   `max(1, ...)` floor), mixed prose+punctuation, and non-ASCII (`héllo`,
   `日本語`) — all pass on both the old and new implementation.
2. `run-agent-ab.ts` and `run-cache-decomposition.ts` produce byte-identical
   headline numbers before and after (same costs, same hit rates, same clean
   counts) — token counting feeds dedup/cap decisions, so "identical," not
   just "close," is the bar.
3. Full suite: 447/447 (433 pre-existing + 14 new).

**Measured delta (same container, same machine, before vs after — this is the
number that's mine to claim; the darwin/arm64 ~22ms row is untouched because I
have no mac to re-measure on):**

| | p50 | p95 | p99 | mean |
|---|---|---|---|---|
| before | 62.70 ms | 79.69 ms | 90.01 ms | 64.66 ms |
| after | ~42.8 ms (3-run avg: 43.86/42.54/41.99) | ~53.5 ms | ~57.9 ms | ~44.4 ms |
| **reduction** | **~32%** | **~33%** | **~36%** | **~31%** |

A quick side investigation (benchmarked separately, not shipped): tried an
ASCII-only fast-path regex (`[A-Za-z0-9']` instead of `\p{L}\p{N}`) to see if
Unicode property escapes were the expensive part specifically. They are not —
only ~7% faster on a representative ASCII sample, not worth the complexity or
the correctness risk of a two-path tokenizer for a single-digit-percent gain.
Not pursued further.

**What's left in `approximateTokenCount`'s neighborhood (profiled, not fixed
tonight — queue for a future hardening night):** the profile after tonight's
fix still shows this one function family at ~43% of CPU. The remaining cost is
structural, not a bug: `reduce-request.ts` calls `countTokens` on the
before-state and after-state of text **separately at every lever stage**
(dedupe-blocks, tool-schema minify/prune, prefix repair, output cap, history
compaction, ...) to report each lever's own token delta for the summary/ledger.
That means a large request's text gets fully re-scanned by the tokenizer once
per lever that touches it, not once overall. This is deliberate — per-lever
delta accounting is what makes a `ReductionChange` auditable — so collapsing
it into one pass would mean restructuring how every reducer reports its own
delta, which is billing-adjacent code and not something to rush in one night.
**Next hardening night: investigate a cheap, correctness-safe way to avoid
re-tokenizing unchanged spans across lever stages** (e.g. a lever that makes no
edit to a substring could skip re-counting it if the prior count is still
attached) — must preserve exact per-lever accounting, verified the same way
tonight's fix was (pinned exact-value tests + byte-identical eval output
before/after).
