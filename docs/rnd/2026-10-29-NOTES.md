## Hardening: per-model cacheable minimum in the simulator's `CachePolicy`

### The gap

`packages/core/src/model-prices.ts` already has
`anthropicCacheableMinimumTokens(modelId)` — the production cache stamp
(`reduce-request.ts`) uses it to withhold a `cache_control` breakpoint on a
Haiku-class request whose stable prefix clears the generic 1,024-token
minimum but not Haiku's 2,048. That fix shipped a few nights ago (see
`2026-10-25-NOTES.md`).

Two other places price caching and never got the same fix:

1. **`packages/core/src/cache-simulator.ts`** — `ANTHROPIC_CACHE_5M` and
   `ANTHROPIC_CACHE_1H` hardcode `minimumCacheableTokens: 1_024` regardless
   of which model the simulated traffic is for. Harmless today because
   every published fixture that uses these policies (`run-agent-ab.ts`,
   `run-cache-decomposition.ts`, `run-workload-matrix.ts`) runs Sonnet-class
   traffic, so the flat 1,024 happens to be correct. A future Haiku-priced
   fixture would silently overstate its caching saving below 2,048 tokens —
   exactly the bug the production stamp was fixed for, reappearing in the
   measurement code that is supposed to catch it.
2. **`packages/core/src/savings-model.ts`**'s `projectSavings` — its
   `minimumCacheableTokens` option defaults to a flat 1,024 for every
   caller, with no way to vary it by model because `projectSavings` takes a
   `TokenPrice`, which carries no model identity. Two real call sites know
   the provider and model and were silently passing neither:
   - `packages/cli/src/main.ts`, the `flux analyse` tool's live path —
     projects savings for a customer's own logged traffic by
     `workload.provider` / `workload.resolvedModel`. If a customer runs any
     Haiku-class Anthropic model, this would overstate their caching
     saving today, on real customer numbers, not just a fixture.
   - `evals/run-analysis-regression.ts`'s two `projectSavings` call sites
     (the regression harness for the same analyser).

### The fix

1. `packages/core/src/cache-simulator.ts`: added
   `anthropicCachePolicyForModel(ttl, modelId)`, which returns
   `ANTHROPIC_CACHE_5M` / `ANTHROPIC_CACHE_1H` with
   `minimumCacheableTokens` replaced by
   `anthropicCacheableMinimumTokens(modelId)` — the same table the
   production stamp already uses. The two named constants are untouched
   (still the Sonnet/Opus-class default), so every existing caller that
   constructs a policy by name keeps its current behaviour; only a caller
   that knows the model and switches to the new function gets the
   model-aware minimum.
2. `packages/core/src/savings-model.ts`: added
   `minimumCacheableTokensFor(provider, model)` (same rule: Anthropic
   defers to `anthropicCacheableMinimumTokens`, every other provider stays
   at the flat 1,024, since OpenAI documents no model-class split). Wired
   it into the three real call sites that know their provider and model:
   `packages/cli/src/main.ts` (both `projectSavings` calls in the `flux
   analyse` report path) and `evals/run-analysis-regression.ts` (both its
   per-workload loop and the round-trips-pricing gate). `run-savings-model.ts`
   also updated for its archetype loop, though its two configured models
   (Sonnet 5.5, gpt-5) were never Haiku-class so this was cosmetic there.
   `run-technique-comparison.ts` left alone — openai-only, no model-class
   minimum to resolve.
3. Tests: `cache-simulator.test.ts` gained two cases — the factory returns
   2,048 for a Haiku-class id and 1,024 for Sonnet, and a direct
   `simulateCache` run showing a ~1,500-token prefix caching under the
   Sonnet policy but reporting `below-minimum` under the Haiku one.
   `savings-model.test.ts` gained the same shape: `minimumCacheableTokensFor`
   resolves correctly per provider, and a 1,500-token stable segment caches
   under the generic default but is correctly withheld once the caller
   passes the Haiku-aware minimum.
