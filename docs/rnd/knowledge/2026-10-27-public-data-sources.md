# Public Data Sources for FLUX Calibration

Day-shift output for the 2026-10-27 strategy dispatch (Q3 data sources).

Engineering reference. Consolidates three independently-verified surveys (chat traffic, agent trajectories, production serving traces) into one ranked list. Every access URL below was fetched live during the underlying surveys and confirmed to resolve; anything a researcher could not confirm resolves is marked UNKNOWN inline rather than guessed, or dropped outright where the whole entry was unconfirmable. "Splitwise traces" is not counted as a separate row — `splitwise-sim` confirms it samples synthetic traces from the Azure 2023 dataset's distributions, so it is the same artifact as row 3, not independent data.

Ranking rule: production serving traces with real provider-reported token counts first (highest value — this is the Q3.1 token-economics-distribution moat), then agent/tool-use trajectories, then chat/instruction traffic last.

## What NO public source gives us

Real per-customer production traffic, priced against that customer's real provider bill, is not in any public dataset above — and cannot be. Every row in this table is either (a) an infrastructure operator's traffic with no cost/billing context (Mooncake, Azure, BurstGPT), (b) a benchmark/trajectory corpus generated against a fixed task suite rather than organic customer usage (SWE-agent, OpenHands, ToolBench, etc.), or (c) UI-scraped chat exports with no request-cost linkage at all (WildChat, LMSYS, Arena, OpenAssistant, HH-RLHF, ShareGPT). None of them pair a specific customer's actual request stream with that same customer's actual invoice.

That pairing — real traffic shape matched to a real dollar figure a customer can verify against their own bill — is obtainable only from pilots. This is the strategic point: the public corpora above can calibrate simulator priors (token distributions, re-emission rates, idle-gaps, tool-schema sizes, quality graders), but they cannot produce or substitute for a defensible, customer-verifiable savings number. That number only exists once FLUX runs against a real customer's real traffic and is checked against that customer's real provider-reported usage and bill — consistent with FLUX's standing honesty rule that published savings claims must trace to a verifiable source, not a public-dataset proxy.

## Structural gaps across all three tiers

- **Tier 3 (chat traffic) carries no system prompts, tool/function-call traces, or native per-message token-count field in any of the six corpora.** This caps them to turn-count, re-emission, and response-length calibration — never cache-prefix-stability or tool-schema-boilerplate calibration, since the real request bodies FLUX's reducer operates on (system block, tool schemas, headers) aren't present in any of these exports.
- **Tier 2 (agent trajectories) carries real multi-turn request/response bodies and real tool schemas, but no dataset in this tier has a confirmed native token-count field** on the public mirrors actually inspected — OpenHands' own local `output.jsonl` format is the one place token usage is documented to exist, but that wasn't confirmed to survive into any redistributed HF mirror.
- **Tier 1 (serving traces) is the only tier with confirmed real provider-reported token counts**, and within it only Mooncake carries a cache/prefix-reuse signal (`hash_ids`) — Azure and BurstGPT have token counts but no cache-hit field, so idle-gap and arrival-pattern calibration from those two is fleet-level only, not per-conversation.
- Across all three tiers, closing the system-prompt / tool-schema / cache-prefix gap requires either wire-captures of actual framework requests (the framework-zoo work already in the repo) or FLUX's own live customer exports — not any of the nineteen public datasets above.
