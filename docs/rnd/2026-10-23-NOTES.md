3. **New-lever research: continuous-learning / continuous-memory agents**
   (founder mandate shape list, item 3). Picked up finding 1 from last
   night's workload-matrix findings doc directly.

   **The gap.** `evals/run-workload-matrix.ts`'s `memoryAgent()` fixture
   re-injects an unchanged ~450-token memory block at the front of every
   user turn — exactly how a framework with a conversation-level "memory"
   concept (LangChain's `ConversationBufferMemory`, a mem0-style memory
   store, or a hand-rolled context block an app glues onto every call)
   actually wires the request when the provider SDK has no separate memory
   channel. None of FLUX's existing levers reach it: `duplicateContext`
   (`dedupeRepeatedBlocks`) only ever sees ONE message's text at a time, and
   the memory block is not a standalone paragraph inside any single
   message — it is the shared PREFIX of many messages that each continue
   differently (`${MEMORY_BLOCK}\nTurn N: ...`). The shape's system prompt
   is also below the 1,024-token documented cacheable minimum, so the cache
   stamp earns nothing here either (confirmed again tonight: see the
   measurement below, arm B vs A is exactly 0.0%). This lever really is the
   shape's only hope.

   **Design.** Added `dedupeRepeatedLeadingBlock` to
   `packages/core/src/token-reduction.ts`: given an ordered list of texts,
   it treats the first as canonical and replaces a repeated LEADING block in
   every later text with a short reference marker, keeping each text's own
   differing remainder verbatim. The cut point is always snapped to the
   last newline at or before the raw character-level common-prefix length
   (never a complete containment match, which needs no snapping) —
   otherwise two turns that merely open with the same few words before
   diverging mid-line (e.g. both starting "Turn ") would have that
   differing line itself truncated, which is a real failure mode a naive
   `commonPrefixLength` cut would hit. Covered by a dedicated test for
   exactly that case.

   Wired into `packages/sdk-js/src/reduce-request.ts` as a new opt-in,
   OFF-BY-DEFAULT config flag: `crossTurnMemoryDedup?: boolean |
   { minimumBlockTokens?: number }` (default minimum 64 tokens). Restricted
   to the `user` role only, deliberately: that is where this pattern
   actually appears, and keeping the lever off assistant/tool bodies avoids
   it fighting with the OTHER lossy levers that already reach those
   (`freshToolResultCap`, `historyCompaction`) over the same bytes. Runs
   before the per-message `duplicateContext` pass so the marker it leaves
   behind is simply inert to that pass, not re-processed.

   **Classified LOSSY, not lossless — this is the important call, and it
   is a deliberate departure from house convention, stated plainly.**
   `dedupeRepeatedBlocks`'s existing same-message dedup calls an exact
   duplicate "lossless" because the duplicate sits immediately next to its
   twin inside ONE string the model reads in one breath. The duplicate this
   lever removes can be many turns upstream of the current one. A model
   that attends less to context far back in a long history may genuinely
   behave differently with the memory block present once near the start
   versus restated fresh every turn — that is exactly the "lost in the
   middle" failure mode, and FLUX's own honesty rule ("quality gates only
   get stricter") means this cannot be waved through on the strength of
   "the bytes are identical" alone. It is also a departure from the
   established rule that lossy levers never touch genuine user-authored
   text (`freshToolResultCap`/`historyCompaction` are explicitly tested
   never to touch user messages): this lever DOES touch user-role content,
   on the judgment that the re-injected memory block is application-level
   injected context riding under the `user` role for lack of a dedicated
   channel, not hand-typed words — but that is a judgment call, not a free
   pass, which is exactly why the lever is opt-in, off by default, and
   gated behind `replayGate` before any part of its saving may be billed
   on real traffic. No replay-gate run happened tonight (there is no live
   customer traffic or API budget in this environment); what shipped is
   the lever, its tests, and an honest simulator measurement — not a
   production enablement.

   **Fixture and measurement.** New dedicated eval,
   `evals/run-memory-agent-dedup.ts`: a 40-turn continuous-memory agent
   (longer than the workload-matrix's 16-turn fixture, to make the
   compounding effect of the earlier turns' repeated block legible), three
   arms, all priced via the simulator at catalogued claude-sonnet-5-5
   prices with caching held UNAVAILABLE throughout (deliberately, to
   isolate this lever's own token effect from any cache effect):

   - **A. raw** (no FLUX): $0.5944.
   - **B. lossless stack** (toolSchemas + duplicateContext +
     repairCachePrefix + 5m cache stamp): $0.5944 — 0.0% vs A, confirming
     the shape really does defeat every existing lever, as finding 1 said.
   - **C. B + crossTurnMemoryDedup**: $0.2496 — **58.0% vs B, 58.0% vs A**.

   Caught and fixed a correctness bug in my OWN eval script before trusting
   this number: the first draft's `wire()` helper only flattened a STRING
   `system` field, but `stampAnthropicCacheTtl` turns a stamped string
   `system` into an array of blocks — so the first draft silently dropped
   the entire system preamble from arm B and C's simulated prompt and
   reported a false saving for B (a lossless arm that should save nothing
   on this shape). Fixed by flattening array-shaped `system`/message
   content the same way `run-workload-matrix.ts`'s own `wire()` already
   does, and confirmed arm B then lands at exactly 0.0%, matching last
   night's own finding. Flagging this pattern for whoever next writes a
   `wire()`-style eval helper: if a lever's code path can turn a string
   field into an array of blocks, the eval's flattener must handle both
   shapes or it will silently under-measure (or over-measure) whatever runs
   through it.

   **Honest framing of the 58% number.** It is real, it is reproducible,
   and it is reported above exactly as measured — but it is a CANDIDATE,
   not a qualified win, and must not be added to README.md or
   docs/site/evidence.md as a published figure. It needs a replay-gate
   pass on a customer's own traffic (grading real responses, not FLUX's own
   token estimate) before any part of it may be billed. Tests added:
   8 in `packages/core/src/token-reduction.test.ts` (including the
   newline-boundary false-positive case, full-containment, fenced code,
   idempotency), 10 in `packages/sdk-js/src/reduce-request.test.ts`
   (off-by-default, never touches assistant turns, works on both
   Responses `input` and Anthropic `messages`, turn-over-turn byte
   stability so the provider's own prefix cache would still match across
   consecutive requests once this and the cache stamp are combined, and
   config-validation skip-on-error). 379/379 tests pass with these added
   (up from 362).

## What the next night should try

- **Replay-gate-prove `crossTurnMemoryDedup` before it can ever be billed.**
  This needs either real customer traffic (per the SaaS model: gated
  per-customer) or, short of that, a credible proxy — e.g. an LLM-judge
  grader comparing real model responses with the memory block present once
  vs restated every turn on a realistic task set, to get SOME quality
  signal beyond "the bytes are identical." Tonight's 58% is a token/cost
  number only; it says nothing about whether answer quality holds.
- Findings 2 and 3 from `2026-10-22-workload-matrix-findings.md` are still
  open and are natural hardening-night (step 4) work, not step 3: (2)
  `dedupeRepeatedBlocks`'s `\n{2,}`-only split misses the RAG fixture's
  single-newline-joined duplicate excerpts — a LOSSLESS granularity fix,
  separate from tonight's cross-turn lever; (3) the production cache-TTL
  stamp (`stampAnthropicCacheTtl`) records a lever change even when the
  stable span is below the per-model cacheable minimum, which is a no-op
  provider-side — needs a small minimum-token table next to the price
  catalogue and a guard before stamping.
- If a future night wants to extend `crossTurnMemoryDedup`: it currently
  only matches a block anchored at the very START of a user message (a
  leading prefix). A memory block injected in the MIDDLE of a user turn
  (prefix is the user's own new instruction, memory glued after it) would
  need a different anchor, not just a prefix match — worth checking which
  pattern real LangChain/mem0-style integrations actually use before
  building that, rather than guessing.
- The next **new-lever** night (step 3, two nights from now under the
  alternation) still has multi-agent fan-out and autonomous long-horizon
