## Hardening: Finding 3 — below-minimum cache-TTL stamp no-op guard

### The bug

Anthropic will not cache a prompt prefix shorter than its documented
minimum — 1,024 tokens for Opus/Sonnet-class models, 2,048 tokens for
Haiku-class models. Below that minimum the request is processed without
caching at all; this is not an error, it is a silent provider-side no-op.
`stampAnthropicCacheTtl` in `packages/sdk-js/src/reduce-request.ts` (the
code that actually places `cache_control` on real customer requests) had
no concept of this minimum at all: it stamped every stable prefix it found
and unconditionally recorded a `cache-ttl-5m` / `cache-ttl-1h` lever,
regardless of whether the prefix was long enough for the provider to ever
actually cache it. That lever claims a saving ("writes bill at 1.25x/2x,
reads at 0.1x") that, below the minimum, can never happen — on real short
prompts this is exactly the kind of thing FLUX's own honesty rule
("quality gates only get stricter," every number traces to a runnable
command) cannot tolerate once it is known. It was already flagged in
`docs/site/evidence.md`'s own open-items list ("Per-model cacheable
minimums not yet simulated → 34.3% may overstate on some models") and in
`2026-10-22-workload-matrix-findings.md`'s Finding 3.

This was not hypothetical. `evals/run-workload-matrix.ts`'s RAG and
memory-agent fixtures were already hitting it for real: the RAG fixture's
~550-token system prefix and the memory-agent's ~450-token re-injected
block are both well below the 1,024-token minimum, and before tonight's
fix the harness's own lever list recorded `cache-ttl-5m` on every one of
those requests, claiming a cache saving on a stamp Anthropic would have
silently ignored.

### The fix

1. `packages/core/src/model-prices.ts`: added
   `anthropicCacheableMinimumTokens(modelId)`, a small table next to the
   price catalogue (as the finding asked for) — 2,048 for any model id
   matching `/haiku/i`, 1,024 otherwise. Matched by substring on the raw
   model id rather than through `resolveModelId`: the minimum depends on
   model CLASS, not on resolving an exact dated build to a priced
   catalogue entry, and a model id the catalogue cannot resolve still has
   a real minimum — the conservative default (1,024, the more lenient
   figure) only applies to ids that are not recognisably Haiku-class.
   Dedicated tests in the new `packages/core/src/model-prices.test.ts`
   (case-insensitive, dated-build-id, unresolvable-id cases).

2. `packages/sdk-js/src/reduce-request.ts`'s `stampAnthropicCacheTtl`: now
   takes `countTokens` and, before placing EITHER candidate breakpoint,
   measures the FULL prefix that breakpoint would cover against the
   per-model minimum:
   - the system breakpoint's prefix is `tools + the stable system text`
     (the volatile tail, when prefix repair split one off, is correctly
     excluded — it was never part of the cached span anyway);
   - the message breakpoint's prefix (multi-turn) is
     `tools + the full system + every message up to and including the
     last one`, captured BEFORE either breakpoint mutates the request, so
     a short system doesn't make the function wrongly assume a short
     overall request.
   A breakpoint under the minimum is simply never placed — no mutation,
   no lever claimed. If NOTHING ends up stamped and at least one candidate
   was skipped specifically for being under the minimum (as opposed to
   there being no candidate at all, which stays silent exactly as before),
   the call site now pushes a `cache-ttl-suppressed` change naming the
   measured token count and the per-model minimum, the same lever id and
   shape the pre-existing volatility-guard suppression already uses — a
   caller inspecting `summary.changes` sees an honest reason, not nothing.

   Deliberately scoped to the production stamping path only. The
   SIMULATOR (`packages/core/src/cache-simulator.ts`) that the published
   bands are computed from still hardcodes `minimumCacheableTokens: 1_024`
   uniformly across all three Anthropic cache policies, with no per-model
   distinction — every published arm (L, M, the workload matrix) runs on
   `claude-sonnet-5-5`, for which 1,024 is exactly correct, so no published
   number is affected either way. Teaching the simulator itself to vary by
   model would touch `savings-model.ts`, every eval script that
   constructs a `CachePolicy`, and `evals/run-agent-ab.ts`'s arm
   L/M plumbing — a real but separate refactor, left for a future
   hardening night (see below). Tonight's fix is specifically for what
   Finding 3 and the evidence.md caveat actually describe: the production
   code recording a lever on traffic it could never have earned anything
   from.

3. Existing tests updated. Several `cacheTtl` fixtures in
   `reduce-request.test.ts`, `cache-volatility-guard.test.ts`, and
   `surfaces.test.ts` used short, hand-written system prompts ("You are a
   support agent.") that were well under 1,024 tokens — correct for
   testing breakpoint PLACEMENT mechanics in isolation, but they would now
   (correctly) never stamp at all once the guard existed. Padded each to
   comfortably clear the minimum (verified against `approximateTokenCount`,
   not guessed) rather than disabling the new guard for them; the surfaces
   test's billing assertions are unaffected because they price a
   mocked provider response's own `usage` field, not the request body's
   size. Added four new tests to `reduce-request.test.ts` for the guard
   itself: a short one-shot system suppressed with a reason citing the
   1,024 minimum; the SAME prefix stamping on Sonnet but suppressed on
   Haiku (proving the per-model distinction, not just a flat constant);
   a short multi-turn conversation with no system prompt at all
   suppressed via the message-breakpoint path specifically; and the same
   shape stamping once the running history alone clears the minimum.
   384 → 390 tests.

### Measured effect

`node --import tsx evals/run-workload-matrix.ts`, before → after (same
fixtures, same prices, nothing else touched):

| shape | before (levers) | after (levers) | cost |
|---|---|---|---|
| rag pipeline | `cache-prefix-repair×40, duplicate-context-removal×40, cache-ttl-5m×40` | `cache-prefix-repair×40, duplicate-context-removal×40, **cache-ttl-suppressed×40**` | −7.5% (unchanged) |
| memory agent | `cache-ttl-5m×16` | `cache-ttl-5m×13, **cache-ttl-suppressed×3**` | −0.0% (unchanged) |
| multi-agent / autonomous / batch | unchanged | unchanged | unchanged (their prefixes already clear 1,024) |

Cost is unchanged on every row, exactly as it should be: the no-op lever
was earning $0 before (a rate-change lever with `estimatedTokensSaved: 0`,
and the simulator never actually granted the write-premium-free read it
implied), so removing the false claim costs nothing — it only stops FLUX
from recording a lever that did nothing as if it had worked. This is the
honest outcome for a hardening fix: the fix's value is in the ledger's
`changes` record being truthful, not in a cost number moving.

`pnpm build` clean; 390/390 tests pass; `run-agent-ab.ts` /
`run-cache-decomposition.ts` headline numbers unchanged (reconfirmed
above) — none of their fixtures' system prompts are anywhere near the
1,024-token minimum, so nothing there was ever mis-stamped.

### Quality gate / replay-gate status

None needed — this is a strict subtraction (a lever that could never have
earned anything no longer claims to), not a new transform on model-visible
content. No replay gate applies; this is the same category as the
pre-existing volatility-guard suppression it shares a lever id with.
