## Hardening: T1 half one — $defs stripped out from under a live $ref

`docs/rnd/lever-backlog.md` §4 T1 names "Tool-schema canonical ordering +
pydantic-aware minifier extension" as the safest unreviewed lever on the list.
Inspecting the existing minifier (`packages/core/src/tool-schema.ts`) for the
"pydantic-aware" half surfaced a real bug, not a missing feature.

### The bug

`PLUMBING_KEYS` included `$defs` and the pruning walk stripped every `$defs` key
unconditionally, recording it as a `lossless: true` plumbing removal ("the model
never reads this"). That is true only when nothing in the tool resolves into it.
Pydantic's `model_json_schema()` (and most JSON-Schema-generating libraries) emit
`$defs` with `$ref: "#/$defs/Name"` pointers from inside `properties` for any
nested, recursive, or shared type — a routine shape for structured-output and
nested-object tool parameters. Stripping `$defs` in that case leaves the `$ref`
dangling: the model is shown a pointer to a type definition that is no longer in
the request. That changes what the model can infer about the parameter's shape —
a behaviour change, mislabeled lossless. Reproduced directly: a `create_user` tool
with `user: {$ref: "#/$defs/User"}` and a `User` definition under `$defs` came out
of `minifyToolSchemas` with the `$defs` block gone and the `$ref` left pointing at
nothing, logged as a plumbing removal.

### The fix

`packages/core/src/tool-schema.ts`: `$defs` is no longer in the unconditional
`PLUMBING_KEYS` set. A new `refersIntoDefs(tool)` walks the whole tool (before
pruning) collecting every `$ref` string value and checks whether any of them point
into `#/$defs` — this covers direct references, nested references, and
self/mutually-recursive definitions (a `$ref` from inside `$defs` back into
`$defs` still counts, since recursive types are a normal shape). `prune` now takes
that per-tool boolean and threads it through every recursive call:

- if `$defs` is referenced anywhere in the tool, it is kept (and still recursed
  into, so genuine plumbing nested inside a kept `$defs` entry — a stray `$id` or
  `$comment` on one of the definitions — is still stripped);
- if nothing in the tool refers into it, the existing unconditional-strip
  behaviour is unchanged, so catalogues that already worked (plain object schemas,
  or JSON-Schema generators that emit dead `$defs` blocks) keep the exact same
  lossless saving as before.

Four new tests in `tool-schema.test.ts`: a referenced `$defs` is kept with its
`$ref` intact; a self-referencing (recursive) `$defs` is kept; a genuinely unused
`$defs` is still dropped and still reported lossless (regression guard on the
existing saving); and one tool's dead `$defs` does not affect a sibling tool's
referenced `$defs` in the same catalogue (the per-tool scoping is real, not
accidentally global). 433 → 437 tests, build and full suite green.

### Published-number impact

None. `grep -rl '\$defs' evals/` returns nothing — no fixture any published
number is computed from contains a `$defs`/`$ref` pair, so this fix changes
no number in `README.md` or `docs/site/evidence.md`. Re-ran
`run-cache-decomposition.ts` after the fix to confirm: identical to the
pre-fix run (37.9% / 57.3%, clean 38/40 both). This is pure correctness
hardening on a path real pydantic-shaped tool catalogues will hit in
production, with zero effect on anything already quoted.
