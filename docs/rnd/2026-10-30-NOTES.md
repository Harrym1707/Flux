# 2026-10-30 — hardening night: per-model Anthropic cache minimum in the simulator

Alternation: the last several nights (10-26 through 10-28/29) were new-lever /
research heavy — crossTurnMemoryDedup, the RAG newline dedup, batch-tier
pricing catalogue, the semantic-compaction prototype, the calibration pass,

hardening night.

## What this picks up

`2026-10-25-NOTES.md`'s own "what next night should try" flagged this
directly: `cache-simulator.ts`'s `ANTHROPIC_CACHE_5M` / `ANTHROPIC_CACHE_1H`
hardcode `minimumCacheableTokens: 1_024` regardless of model, even though the
module's own doc comment already says "2,048 on Claude Haiku" and the
production stamping path (`reduce-request.ts`, via
`anthropicCacheableMinimumTokens` in `model-prices.ts`) has enforced the
Haiku split for a while. Harmless today because every published fixture runs
a Sonnet-class model (1,024 is exactly correct for those), but a flat
constant silently overstates caching on anything in [1024, 2048) tokens for
a Haiku-class workload — the same overclaim shape the production-path guard
was built to prevent, just not yet mirrored in the simulator that the
published bands are computed from.

## What shipped

`packages/core/src/cache-simulator.ts`: two new factory functions,
`anthropicCache5m(modelId)` and `anthropicCache1h(modelId)`, that build a
`CachePolicy` identical to the flat constants except
`minimumCacheableTokens` is resolved per model via the *same*
`anthropicCacheableMinimumTokens` the production path already uses — one
rule, not two. The flat `ANTHROPIC_CACHE_5M` / `ANTHROPIC_CACHE_1H`
constants are untouched; no existing call site (any eval script, or
`savings-model.ts`'s own independent `minimumCacheableTokens` option) was
changed, because all of them are either Sonnet-class fixtures (where 1,024
was already correct) or unrelated to this policy object entirely. This is
deliberately the minimal slice: it makes a Haiku-aware simulation possible
without the larger refactor `2026-10-25` flagged (threading a model id
through every eval script's policy construction) — that refactor is only
needed the day a published fixture actually wants to price a Haiku-class
workload, which none does yet.

`packages/core/src/cache-simulator.test.ts`: five new tests. A sub-2,048,
over-1,024 shared prefix (filler(600) ≈ 1,200 tokens under
`approximateTokenCount`) caches under the flat constant and under
`anthropicCache5m` named as a Sonnet-class model, but is correctly refused
(`missReason: "below-minimum"`) under `anthropicCache5m` named as a
Haiku-class model — proving the per-model distinction actually branches, not
just that a constant exists. Same pair repeated for `anthropicCache1h`. A
fifth test pins the flat constants' own minimum at 1,024 so a future edit
can't quietly change the Sonnet-class default while "fixing" something else.
438 total tests (433 → 438).

## Measured effect

None, by design, and confirmed: `node --import tsx evals/run-cache-decomposition.ts`
before and after this change produces the identical 37.9% cache-only figure
(and `run-agent-ab.ts`'s full table is unchanged too), because no existing
call site's policy object changed — only new, unused-by-default functions
were added. This is the correct outcome for a hardening fix: the fix's value
is that a Haiku-class simulation run (today: none exist) would no longer
silently overstate caching, not that any currently-published number moves.

`pnpm build` clean; 438/438 tests pass.

## Quality gate / replay-gate status

None needed. This changes nothing a model ever reads — it only corrects how
the SIMULATOR polices its own minimum for a model class no published
fixture currently exercises. Same category as the 10-25 production-path fix
it mirrors: a strict tightening of an honesty guard, not a new transform.
