## New-lever research: multi-agent fan-out cache races

### Workload shape studied

**Multi-agent teams — sub-agent fan-out re-sending shared context.** Not
previously covered: `evals/run-agent-ab.ts` covers single-agent sequential
turns, `evals/run-memory-agent-dedup.ts` covers continuous-learning/memory
re-injection, and `docs/rnd/lever-backlog.md` already logged a **REJECTED**
finding on *cross-agent relay cache-sharing* ("relay content differs per
agent role; no shared-prefix win — do not pursue"). That rejection is about
a different mechanism (relayed content differing per role) and does not
cover the one studied tonight.

Grounding (WebSearch + WebFetch, Claude Agent SDK subagent docs, LangGraph/
CrewAI commentary): a subagent's context is NOT empty but is NOT the
parent's conversation either — it inherits the project's CLAUDE.md-
equivalent instructions and the team's tool definitions, fresh, every time
it's spawned. When an orchestrator fans a team out in parallel (Promise.all,
LangGraph's Send API, CrewAI's parallel tasks), every sibling therefore
carries an **identical** system+tools prefix (plus often an identical team
briefing — a ticket, PR diff, or design doc handed to the whole team) and
differs only in its own short role instruction.

### The mechanism, and why it's new work, not already covered

Provider prompt caching is a WRITE that only becomes readable by another
request once the writing call's response has come back. Sequential turns
(`run-agent-ab.ts`'s whole workload) already have that latency baked into
their real inter-turn gap, so MESH's existing cache stamp works exactly as
measured there. Concurrent fan-out does not: N sibling calls can all be
in flight to the provider before ANY of their writes have committed, so
**none of them can read a sibling's write** even though they share the
same content. `packages/core/src/cache-simulator.ts` had no way to express
this — its loop let any later-processed request read an earlier one's write
instantly, which is correct for sequential traffic but silently too
generous for genuine concurrency. Fixed with a new, OFF-BY-DEFAULT option:

- `simulateCache(..., { cacheCommitLatencySeconds })` (default `0`, so every
  existing call site and every previously-measured number is byte-for-byte
  unaffected — verified: 523/523 tests still pass, both regression evals
  reproduce their exact prior numbers after the change). A cache write is
  only visible to a later request once `cacheCommitLatencySeconds` has
  elapsed since the write. A new `missReason: "commit-lag"` distinguishes
  "a sibling write exists but hasn't committed yet" from a genuinely absent
  prefix, so the eval output says WHY a call missed, not just that it did.
  Tests: `packages/core/src/cache-simulator.test.ts` (3 new cases).

### The lever: `planFanoutPrewarm`

`packages/sdk-js/src/fanout-prewarm.ts` (new, exported from the SDK index,
8 tests in `fanout-prewarm.test.ts`). Pure, synchronous, no network call:
given a batch of requests about to be dispatched together, it checks
whether they share one exact `{system/instructions, tools}` prefix above
the provider's cacheable minimum, and if so returns a single minimal
"pre-warm" request (same prefix, trivial instruction, output capped at 4
tokens) plus the original batch UNCHANGED. The caller awaits the pre-warm,
then dispatches the batch exactly as it would have anyway. Declines to act
(returns `prewarm: null` with a `reason`) on a batch too small to race, a
batch that doesn't actually share a prefix, or a shared prefix below either
provider's cacheable minimum — never guesses.

This is why it's **lossless by construction, not by gate**: it never
touches a byte of the N real requests, only adds one extra lightweight call
before them. Scope boundary, honestly: this is the planning primitive, not
a wired-in proxy behaviour — MESH's proxy sees one request at a time and
has no visibility into a caller's own fan-out, so actually awaiting the
pre-warm before dispatch is the calling code's (or a future framework
adapter's) job. Shipping that adapter is follow-on work, not claimed done
here.

### Fixture and measurement

`evals/multiagent-fanout-fixture.ts` (new): 40 independent fan-out rounds
(a fresh "ticket" each round, so cross-round prefix sharing is a measured
~68 tokens — safely below the 1,024-token minimum, verified before trusting
any number below) x 5 sub-agents each, sharing a ~2,400-token prefix within
a round (project rules + ticket briefing + 4 tool schemas). Dispatch spread
0.01s (generous for a real `Promise.all`), commit latency 2.5s (**ASSUMED**
— no provider publishes this; lower-bounded by a completed response, and a
~380-token sub-agent turn is not instant).

`evals/run-multiagent-fanout.ts` (new), three arms, decomposed exactly so
the lever's contribution is never confused with "caching is on":

```
A. no MESH (uncached)                            $1.365
B. MESH cache stamp, naive concurrent fan-out    $1.517   <- WORSE than A
C. MESH cache stamp + fan-out prewarm (the lever) $0.977

B vs A (cache stamp ALONE, no sequencing fix): -11.1%  NEGATIVE, logged honestly
C vs B (adding the prewarm barrier):            35.6%
C vs A (the full lever vs no caching at all):   28.4%
```

**The honest, unflattering half of this result**: simply turning MESH's
cache stamp on for this workload shape, with no sequencing fix, is a
**measured loss** (-11.1%) — every sibling independently pays the provider's
write premium (1.25x) and none ever reads a sibling's write back. Per
doctrine ("a lever that loses money counts against FLUX"), this is logged,
not hidden: `run-multiagent-fanout.ts` asserts arm B is a loss and fails
loudly if a future change makes that stop being true, so nobody can quietly
make stamping default-on for fan-out traffic without re-deriving this.

**The lever's win**: adding `planFanoutPrewarm`'s barrier converts those
same write-premium losses into read discounts — **28.4% cheaper than no
caching at all, 35.6% cheaper than naive stamping.**

Sensitivity (the headline number rests on one guessed commit latency; swept
0.5s–10s, dispatch spread held at 0.01s): **identical result at every
tested latency** (B vs A -11.1%, C vs A 28.4% throughout). The finding is
not a knife-edge — it holds as long as sibling dispatch stays far below
commit latency, true across the whole plausible range for an agent-team
turn (never sub-second).
