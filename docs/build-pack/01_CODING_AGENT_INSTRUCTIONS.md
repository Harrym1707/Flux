# FLUX --- Coding Agent Instructions

You are the primary coding agent for the FLUX repository.

## Mission

Build FLUX as production-grade infrastructure software that reduces AI
inference cost while preserving customer-defined quality.

## Absolute rules

1.  Never silently change model, prompt, context or execution policy in
    production.
2.  Every optimisation must have an explicit policy and version.
3.  Every optimisation must be reversible.
4.  Unknown workloads use the customer's baseline path.
5.  Never optimise solely for token price.
6.  Never claim quality equivalence without evaluation evidence.
7.  Deterministic evaluation is preferred over LLM-as-judge.
8.  Keep the data plane fast and boring.
9.  Move expensive analysis to asynchronous workers.
10. Treat tenant isolation and privacy as first-class requirements.

## Development order

### Phase 1 --- SDK

Implement: - provider interception - request IDs - metadata collection -
async telemetry - baseline pass-through

### Phase 2 --- Control plane

Implement: - applications - requests - models - task classes - costs -
policies

### Phase 3 --- Evaluation

Implement: - dataset creation - baseline/candidate pairs - evaluator
interface - deterministic evaluators - model-based evaluator -
confidence intervals - regression detection

### Phase 4 --- Routing

Implement: - policy lookup - candidate eligibility - deterministic
routing - percentage rollout - escalation - rollback

### Phase 5 --- Optimisation

Implement: - context optimisation - semantic caching - agent budgets -
retry optimisation

### Phase 6 --- GEO/GTM

Implement: - benchmark publishing pipeline - documentation site -
integration pages - comparison pages - machine-readable product
metadata - AI visibility measurement

## Coding style

Prefer small modules.

Bad:

``` ts
router.ts
// 2,000 lines containing routing, evaluation,
// provider calls, persistence and analytics
```

Good:

``` text
router/
  candidate-selector.ts
  policy-loader.ts
  rollout.ts
  escalation.ts
  rollback.ts
```

## Interfaces first

Before implementing a subsystem, define its interface.

Example:

``` ts
interface Evaluator {
  name: string;

  evaluate(input: EvaluationInput): Promise<EvaluationResult>;
}
```

## Testing requirement

Every optimisation needs:

1.  unit tests
2.  integration tests
3.  replay tests
4.  regression tests
5.  rollback test

No optimisation is production-ready without proving rollback.

## Safety invariant

For every active optimisation:

``` text
if quality < policy.minimumQuality:
    rollback()
```

Hard constraints always override savings.

## Observability

Every routing decision should be explainable.

Store:

``` text
policy_id
policy_version
candidate
baseline
decision
reason
quality_evidence
cost_estimate
rollout_percentage
```

A customer should be able to answer:

> "Why did FLUX send this request to this model?"

without reading source code.

## Privacy

Do not log raw prompts or outputs unless the customer explicitly enables
content capture.

Use hashes/fingerprints for:

-   prompt identity
-   system prompt identity
-   task identity

Support metadata-only mode.

## GEO/GTM coding requirement

The public documentation system is part of the product repository.

Every benchmark generated by the system must contain:

-   benchmark date
-   models tested
-   model versions
-   dataset description
-   sample size
-   evaluation methodology
-   cost assumptions
-   quality metric
-   latency metric
-   limitations

Never generate SEO pages with invented statistics.

The GEO system should turn genuine engineering work into public
technical evidence.

## Definition of done

A feature is done only when:

-   implementation exists
-   tests pass
-   telemetry exists
-   failure behaviour is defined
-   rollback exists where relevant
-   docs exist
-   API contract is documented
-   security implications are reviewed
-   cost implications are measurable
